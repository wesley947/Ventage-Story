# Client-only audio on vanilla server: feasibility audit

## Released engine follow-up — 2026-11-14

The shipped 1.22.7 binary review in [Server audio transport](SERVER_AUDIO_TRANSPORT.md) addresses the implementation inspection below. The native arbitrary one-shot packet is server-to-client. The inspected vanilla client-to-server paths offer built-in actions but no supported generic sound request. The server can send frame-cued stock sounds in entity animation metadata when it controls that definition. D63 and the listening question for stock emotes remain open as release criteria.

**Audited:** 2026-11-09. **Hard user requirement (D63):** exactly one player has the client-only Cabbage Carnage mod; the server has no Cabbage Carnage/Fart Lab code and every other nearby player is unmodded; nevertheless those other players hear the sound. Do NOT weaken this requirement to a mod installed on the server, even when clients are unmodded.

## Crucial separation

- **Client-originated** does not mean **client-provided sounds are forwarded**. Multiplayer clients normally send commands, controls, inventory/item/block interactions and selected entity packets; the server runs its **existing handlers** and decides what to send to other clients. Clients do not communicate directly with one another.
- **Actual verified local trumpet test does not meet D63:** `PlayerGasStateModSystem.ShouldLoad(Server)` uses `serverApi.World.PlaySoundAt(game:sounds/voice/trumpet, entity, null, pitch, 20f, volume)` in the singleplayer integrated server. The sender's local client only rendered the native sound; the singleplayer integrated server did all the broadcasting.
- Sound must be **already present on the vanilla listener** and be invoked via a **vanilla-recognized server action**, such as emote/voice or normal item/block interaction. Client `World.PlaySoundAt` is only local to that client. No public API lets lone client ask a vanilla server to relay an arbitrary file path, ADSR JSON, pitch/time sequence or streamed audio to vanilla listeners.

## Examined upstream channels and sound producers

| Mechanism | Client→vanilla-server path | Remote vanilla listener | Parameters/fatal limitations |
| --- | --- | --- | --- |
| **`/emote` player voice** | Vanilla recognized chat command (e.g., `/emote shrug`, `/emote laugh`, `/emote rage`, `/emote wave`) accepted by server | Native `EntityServerPacketId.Emote` event causes `EntityPlayer.OnReceivedServerPacket` to invoke `EntityTalkUtil.Talk` (client-side sample synth) | **BEST current no-item route.** Vanilla shapes exist: `Shrug` rises 0.9→1.5 in 0.6s; `Complain` many short notes; `Laugh` repeated high notes; `Meet` random upward slides. Instrument/pitch from player's saved `voicetype` and `voicepitch`. No arbitrary pitch/volume IDs per request; emote animation may be visible; mouth/head source not rear. Send responsibly, no spam. Actual unmodded remote client **not yet tested by us**. |
| **Character voice selection** | Vanilla `charselection` network channel, validated by `CharacterSystem.onCharacterSelection` on server | Server `WatchedAttributes` (`voicetype`, `voicepitch`) configure each remote `EntityTalkUtil` | 7 voice instruments and 5 discrete pitch categories (`verylow`=.6, `low`=.8, `medium`=1, `high`=1.2, `veryhigh`=1.4). **Server gate:** changing selection after initial choice requires `allowcharselonce` or Creative; cannot assume continuous instrument/pitch switching in Survival. Do **not** send invalid character-selection updates or rely on bypassing server restrictions. |
| **Vanilla bone flute** | Legitimate held-item right-click: `ItemFlute.OnHeldInteractStart` runs on client and server; uses `World.PlaySoundAt(sounds/instrument/elkcall, byEntity, player, pitch=.75, range=32, volume=.5)` | Ordinary nearby listeners should hear the server-side instrument clip | **A real server-routed sound example**, no custom mod on server/listener, but requires actual bone flute in player's hand and its four-second cooldown. Fixed native elk call, can't substitute arbitrary fart sample or pitch parameter; may also summon an owned elk. |
| **Footsteps / combat / tool / food / blocks** | Normal gameplay controls and hand/entity/block interaction; server executes game behavior | Native `PlaySoundAt` on server or replicated game state | No general choice of arbitrary sound; choice follows genuine action, actual item/block/terrain, server logic. Footsteps locally predicted and server-routed with `dualCallByPlayer` to avoid duplicate playback. Damage grunts require real damage. |
| **Animation-attached sound metadata** | `AnimationSound` and `AnimationMetaData` declare per-frame native sample/pitch/volume/loop and serialize for server-owned animations | Remote clients can play sounds tied to vanilla server-synchronized animations | Interesting **data model**, but no public client→unmodified-server API to register new animation-sound metadata. `PlayerAnimationManager` manipulates locally loaded animation definitions; `AnimationManager` sends animation state from **server**. Do not assume a client-added sound array will be trusted or sent to peers. |
| **Resonator/music cylinders** | Legitimate placement/interactions, server-owned block entity and actual music-disc ItemStack | Client reads synchronized `BEResonator` inventory and starts the **recognized** music track | Uses `ItemAttributes["musicTrack"]` defined by the actual vanilla collectible, not arbitrary client-supplied sound; requires in-world machine/cylinder, not wearable event. Not suitable as a transparent fart broadcast. |
| **Entity Activity System play-sound action** | Server/authorized behavior configuration can choose a sound path | Server `PlaySoundAt` if configured action executes | There is a powerful `PlaySoundAction.soundLocation` parameter, but it belongs to activity scripts/editor configured on server. A client-only mod cannot supply new actions to a vanilla server. |
| **Raw entity/block packets, custom channel** | `IClientNetworkAPI.SendEntityPacket`, `SendBlockEntityPacket`, `RegisterChannel`, `SendArbitraryPacket` all transmit TO the server | Only if vanilla server has an appropriate handler | `EntityPlayer.OnReceivedClientPacket` handles known native IDs (e.g. `SitfloorEdge=296`); voice `TalkPacketId=1231` and emote packet 197 are **server→client**, NOT client-controlled playback RPC. Registering a private channel solely on client does not add a handler to vanilla server. `SendArbitraryPacket` is a low-level transport API, not a general sound permission. |
| **Client `.debug talk`** | Local command only | **No** remote sound from this test | Useful for local audition, not proof of multiplayer audibility. |
| **Third-party instruments/proximity voice mods** | Their own client/server channels and event handlers | Other players generally need relevant compatible mod/client and/or server-side support | Does NOT satisfy user no-other-mod requirement. Spivohrai explicitly requires listeners to have its mod. |

## What remains open

1. **Top priority minimal multiplayer test:** One unmodified dedicated server, a client with only a **client-side observational test mod** (not current `server-only` gas mod), and a truly unmodded second client. Have sender trigger `/emote shrug`, `/emote laugh`, `/emote rage` normally and check other player hearing/position/duration. Note server restrictions or command cooldowns. Do not need to start with Fart Lab.
2. **Audition native voice options on test character:** Tuba/trumpet/accordion/clarinet at LOW/VERY LOW pitch (via legitimately allowed character selection) with available emote patterns. Determine if any actually sound like fart-like rumbles/squeaks when heard by clean clients. Voice changes may not be allowed freely after setup; don't assume they are per-fart presets.
3. **Actual held-item audit:** With genuine bone flute, test `/` no custom sound command required; right-click normally and see what remote player hears. The elkcall might be less useful than emote voices, but tests another accepted audio path. Do not simulate having items you lack.
4. **API uncertainty:** Public `vsapi` and `vssurvivalmod` do not contain the entire closed-source engine's internal packet handler logic. We cannot prove an absolute mathematical impossibility from public source alone; current evidence strongly excludes any **documented supported** arbitrary custom-sound relay. Inspect installed 1.22.7 binaries or ask VS developers whether an unrestricted vanilla client→server sound RPC exists, before declaring final hard no.
5. **Sound-quality acceptance:** If vanilla emotes/item sounds are not convincing as flatulence, these workarounds fail D63 in spirit even if they prove native remote audio. A flexible JSON library of arbitrary pitch envelopes can be built locally but **cannot be guaranteed remotely to unmodded clients** without a matching vanilla protocol.

**Decision:** Preserve D63. Do not begin a large sound composer or recast the project as server-installable without the user's explicit choice. The goal is an actual audible fart for vanilla listeners, not a locally rendered fart accompanied by an unrelated remote emote.
