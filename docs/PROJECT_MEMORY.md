# Project Memory — Vintage Story Digestive-Gas Mod

**Last updated:** 2026-11-08  
**Status:** Planning/bootstrap; no confirmed compiled mod or public release. Approved internal Mod ID: `lingamsdigestivesim`; public display title remains undecided.

## Purpose
Create a humorous but carefully engineered digestive-gas simulation for Vintage Story 1.22.x (C#/.NET 10). Include players and eligible ground animals, vanilla and optional third-party species; keep player effects cosmetic. The creator wants a consistent **Lingam's ...** public naming identity for original full mods. The exact display title is unsettled; *Cabbage Carnage* and *Ventage Story* were previous working titles. The existing GitHub repository is named `Ventage-Story` and the approved permanent internal Mod ID is `lingamsdigestivesim`. Do not conflate repository name, mod ID, and final display name.

The first public release should include some well-crafted in-world *Great Silence* lore. Audio samples can be placeholders during development but should be revisited before release.

## Essential simulation invariants
1. **Food intake, production, upper/lower storage, and gas release are separate stages.** Movement and fear affect release probability, not magical gas generation.
2. **Overlapping meals are additive.** New food never zeroes existing gas or restarts prior food contributions. Each consumed portion has its own upper/lower gas *potential* and progress over game time. The contributions still being digested can be compactly stored. Completed contributions can be pruned after accounting for all gas they produced; do not silently discard unproduced gas.
3. Upper gas (belching) may appear earlier than intestinal gas (flatulence). Timing, magnitude, food influence, and species physiology remain to be researched and tuned.
4. A little baseline spontaneous gas may develop even without a detected high-gas meal. It should be rare enough to preserve surprise and not create a steady chorus.
5. Both reservoirs are depleted by releases; **zero available gas means no release**. Slow/calm creatures can accumulate and occasionally release a larger amount; movement, jumping, being scared/chased increases the chance of a small stored-gas release, but it must remain uncommon. Use cooldowns.
6. Death may trigger **one optional delayed postmortem release**, using remaining reservoir gas, several seconds later. No guaranteed postmortem sound when the reservoir is empty. Confirm death lifecycle and cancel/skip safely if the entity unloads or no longer exists. Bowel contents/dung are not in v1.
7. Game time controls digestion. For loaded entities, periodically process elapsed time; after unload/reload, account for missed digestive progress without replaying old noises or fabricating precise movement history. Honor reservoir capacity and avoid double counting.
8. Server owns authoritative digestive state using the game's per-entity persistence mechanism (candidate: `Entity.Attributes`; verify API and save semantics in installed 1.22 build). Only synchronize what clients need.
9. Creature herd audio budget / positional sound / cooldowns should prevent a 30–40-goat pen from becoming deafening. Audible effects must not be the sole representation of physical release.
10. World gameplay and nutrition must stay intact. Player effects should not cause damage, movement penalties, survival disadvantages or other punitive mechanics.

## Fart-roll rates, computational cost, and durable entity saves (2026-11-08)

**User's latest concerns:** The previously proposed 0.2%/0.5% per 15s rates may be **too low** for entertaining gameplay. There is no numeric restriction to integer-percent rates; C# probabilities can be arbitrary floats/doubles, but the user wants chances that matter rather than negligible odds. Processor overhead should stay minimal, particularly with ~40 penned goats; persistence must survive world saves, player login/logout and loading/unloading animals. All values below are **experimental examples, not user-approved balance**.

**Alternative probability framing:** Express natural idle/moving chances as **per active real minute** for intuitive tuning, e.g. pressure 25%→1%, 50%→3%, 75%→6%, 100%→15%, 115%→35%, >=125%→actual emergency release. Convert to a longer/shorter interval without changing odds: `p_interval = 1 - (1 - p_minute)^(elapsedSeconds / 60)`; no per-frame random samples. For 40 goats all at 50% and eligible, 3%/minute corresponds to **1.2 expected successful rolls per minute before cooldowns**; at 40 goats with a 30s heartbeat there are only **80 normal chance checks/minute**. Evaluate additional debounced movement triggers, but not every frame or movement animation step. Animal per-entity update phase should be staggered or randomized to prevent simultaneous releases and CPU spikes. Optimize expensive food history inspection, world/entity scans, logs and actual overlapping sound playback, not trivial RNG. Separate game-time digestion progression from real active-second flatulence opportunity scheduling.

**Verified from public VS API source:** [`Entity.cs`](https://github.com/anegostudios/vsapi/blob/master/Common/Entity/Entity.cs) declares `Entity.Attributes` as "**Permanently stored entity attributes that are only client or only server side**" and `Entity.WatchedAttributes` as "**Permanently stored entity attributes that are sent to client everytime they have been changed**". `Entity.ToBytes(BinaryWriter, bool forClient)` writes **both** watched attrs and, when `!forClient`, `Attributes.ToBytes(writer)`; `FromBytes` reconstructs them (verify ordering/versioning). This makes a **mod-namespaced subtree under server-side `Entity.Attributes`** a strong candidate for durable private digestion state, subject to a compile/in-game persistence test in the installed 1.22.7 API. For modest self-visible UI, mirror only derived qualitative pressure to `WatchedAttributes` when needed—do **not** sync the entire food history and per-entity timer details to everyone. [`EntityBehavior.cs`](https://github.com/anegostudios/vsapi/blob/master/Common/Entity/EntityBehavior.cs) exposes `OnEntitySpawn`, `OnEntityLoaded`, `OnEntityDespawn` and `OnGameTick` hooks for lifecycle adapters, although attaching a mod behavior to all eligible vanilla/modded entities is still unverified.

**Proposed persisted schema (versioned per actor, not yet implemented):**
- `schemaVersion` for evolution/migrations.
- `storedGas` high precision nonnegative numeric amount; never clamp/discard; only actual release decrements it.
- `lastAdvancedTotalHours` in-world game time, so a loaded actor can progress food fermentation/background accrual across calendar skips, and updates never double-count after reload.
- Bounded collection of **active mixed-food digestion batches** with meal entry time, ingredient amounts/profiles and cumulative generated amounts; only remove when all future gas potential is accounted for. Don't save enormous historical logs.
- For **players**, an optional `openIntakeSession` storing included foods and quantities plus **remaining active real-time seconds** until sliding 30s inactivity closure; record immediately on each successful bite, so saving/logout before 30s doesn't lose food. The precise resume/close policy (continue 30s countdown on next live session or finalize safely at logout) remains to be decided; never mis-timestamp closure or burn food. There is no such window for animals.
- Any state needed for cooldown/last release or random-check scheduling to avoid restart exploits and simultaneous herd release. Transient sound handles and UI state are never persisted.

**Save/load algorithm:** Every time source digestion produces gas, add to stored amount and update `lastAdvancedTotalHours` atomically in the persistent state. Every successful fart event subtracts **only actual release amount** and records relevant cooldown metadata. State is stored on the server in the entity's attributes and gets serialized by normal world/entity saves; on load, deserialize and validate version/values, compute the *difference between past and current* `Calendar.TotalHours` and apply at most the cumulative pending food/background production (no replay of earlier random sounds). Test: 16 rapid carrots, mixed carrot/peanut batches, player save/rejoin while intake window open, mid-fermentation reload, long-unfed goat unload/reload, pressure over 100%, and state after two save/load cycles. A game crash before its next world save can still lose recent progress, as with other unsaved game state; don't promise instantaneous disk durability.

**Current milestone focus:** No code for persistence yet. When implementation starts, prioritize one small server-authoritative persisted `storedGas` + `lastAdvancedTotalHours` value on one player and one goat, then add batches and event rolls. Treat game calendar versus real-time countdown resets carefully.

## Movement- and time-triggered fart opportunity model (2026-11-08)

**User direction (confirmed as a design requirement):** Above a proposed **25% of species-normal-full** stored-gas threshold, eligible players and land animals should have a **random chance of natural flatulence throughout ordinary life**, including when standing still, plus **additional opportunities tied to movement**, especially jumping and squatting. Running/walking/moving/fright and transitions should matter. All rolls require genuine positive reservoir gas and **unsuccessful rolls consume zero gas**. Release consumes only the quantity actually expelled; all unused gas persists. The exact 25% lower bound and numeric chance table are **illustrative/tunable**, not finalized by user.

**Proposed implementation (tuning experiment, not approved values):**
1. For loaded/active entities, schedule a **real-elapsed active-world-time opportunity** at a coarse fixed interval (e.g. one 15-second check), NOT once per client/server frame and NOT once per digestion game-hour. Decide pressure-dependent base probability at that moment; adjust for standing, walking, sprinting, animal resting and species to avoid a mechanical periodic chorus. Some random phase jitter per entity, never synchronized herd.
2. Extra **edge-triggered opportunities** on a discrete **jump or landing** (one per jump, not both), **crouch start/hold**, **stand transition**, and meaningful **fright/sprint transition**. Use per-action debounce and an ordinary release cooldown to prevent repeated event/fart spam; the existing deliberate >1s high-pressure crouch and >=2s low-pressure crouch rules take precedence to avoid double-dipping a manual crouch and a separate random roll. Verify server-detectable controls versus client-only state.
3. Pressure = `storedGas / normalFullForSpecies`; chance rises substantially approaching full and overfull, with **emergency large actual release** at/near 125%. Proposed example *per 15-second natural opportunity*: 25% → 0.2%, 50% → 0.5%, 75% → 1.5%, 100% → 5%, 115% → 20%; >=125% emergency case separate. **These are not approved probabilities** and must be tuned against 40 penned goats and multi-player game feel. Interpolate smoothly between knots or implement a hazard-rate model so different check intervals yield equivalent overall chance.
4. **Choose whether a fart happens and how much is expelled separately**: small incidental moving/jump events could emit a minor fraction (e.g. 5–10% of current reservoir), regular spontaneous releases moderate (e.g. 15–35%), overpressure >=50% (often more). Never subtract gas on a failed roll. Release amount and sound category depend on reservoir/trigger/species; preserve biological production schedule independently of event chance.
5. **Cooldowns** govern frequency of actual release or eligible attempts, **never stop gas generation or clear stored gas**. Emergency overpressure may supersede ordinary cooldown. A skipped/unloaded period accumulates digestion/background gas on next update but should **not replay a queue of missed random sound opportunities**. State after catch-up must still honor 125% pressure objective via a single properly accounted real release if necessary.

**Clock separation:** digestion and stomach/gut transit use `Calendar.TotalHours` (game-time), while incidental sound opportunities and action debounces can be based on **elapsed active simulation real seconds** for player-facing consistency across world day-speed settings. Exact heartbeat/check duration can change without distorting event rates if probability is adjusted as `1-(1-p)^(elapsed/interval)` or a hazard model. Do not use FPS as a random sample count.

## Soft full threshold and emergency explosive release (2026-11-08)

**User direction:** Define a normal **"Full" gas reference level = 100%** for both animals and players, **not a hard clamp**. Gas can continue accumulating into an overpressure zone above 100%; as it approaches **125% of normal full**, the probability/urgency of a **large/explosive natural fart** should rise to **almost 100%**, with an ensuing large actual release that removes **at least 50% of current stored gas** (possibly more). User does **not** want levels to rise much above 125% without that substantial relief. This is a user-chosen **target behavior**, with exact probability curve, cadence, percentage of release, and whether the >=125% event becomes guaranteed all still to be specified/tested.

**Design interpretation proposed for implementation:** Pressure = reservoir / species-dependent NormalFullGas; below full, normal chance of small/medium releases subject to activity, fear, crouch, and cooldown. Above 100% choose a strongly accelerating probability of a big spontaneous fart; at >=125% consider a **guaranteed/priority emergency release** that overrides routine sound-event cooldown (subject to safety & only if reservoir positive), releasing e.g. **50–75% of current reservoir**, to keep practical pressure from exceeding the desired bound. Always subtract **only through a real Release event** with sound/visual emission when observers are present; never `Min(reservoir, capacity)` or silently delete overflow. Pressure/risk chances must be measured **per meaningful evaluation opportunity/time interval**, not per raw frame, to avoid FPS-dependent behavior. Evaluate event after calendar-time catch-up in a bounded manner; avoid queued replay of missed sounds when unloaded, and do not pretend arithmetic truncation is a fart.

**Illustrative case:** A goat has 122 units with normal full = 100, accumulates to 125; a big release consuming 60% of 125 = 75 units leaves **50**. Continual background accumulation proceeds afterward regardless of cooldown. For a creature with smaller/larger normal capacity, use the same ratio but species-specific absolute volumes.

No numeric probability ramp, guaranteed emergency handling or release fraction distribution has yet been approved beyond user's guidance (near-certain by 125%, at least 50% relief). Investigate client/server tick timing and time skips before choosing strict maximum guarantee. Confirm distinction between **not much above 125% under ordinary active play** and temporarily overshooting in large skipped game-hour intervals; never sacrifice conservation to impose the bound.

## Gas mass-conservation invariant: only flatulence removes stored gas (2026-11-08)

**Explicit user requirement (hard invariant):** For **players and every eligible animal**, intestinal gas **never disappears merely because of time, a release cooldown, a food contribution expiring, a sleeping/unloaded interval, or a reservoir capacity limit**. Continuous and delayed **gas production always adds to the existing persistent reservoir**. The **only** way for accumulated gas to leave the reservoir in the first-release simulation is an actual flatulence event that explicitly subtracts the **quantity released**, potentially part or all of the stored total. A release can be small, large, natural or crouch-driven, but it must not consume gas that isn't present. Release cooldowns suppress or rate-limit *release events only*; they NEVER pause or erase gas production.

**Canonical accounting rule:** `storedGasAfter = storedGasBefore + gasProducedFromFood + backgroundGasProduced - gasActuallyReleased`, with `0 <= gasActuallyReleased <= storedGasBefore + newGas`. If no release occurs, `storedGasAfter >= storedGasBefore` regardless of cooldown. A source food's gas-production curve is finite, but once generated its gas is not tied to that source's lifetime. In a long-unfed penned goat, a slow baseline continues raising stored pressure; higher pressure can increase chance/size of *natural* expulsion, not silently leak away. Persist across save/reload, entity unload and offline game-time catch-up. No retroactive auto-playing of missed farts; actual state transitions need clear policy.

**Capacity/overflow safeguard:** Previous tentative notes mentioned `reservoir caps` / `capacity overflow` and easing existing gas via absorption. **These are superseded to the extent they permit gas to vanish.** Distinguish `comfortableCapacity` / high-pressure threshold used to increase likelihood or urgency of actual flatus from an absolute numeric storage clamp that deletes accumulated gas. Prefer soft capacity or separate overflow bookkeeping which preserves total amount until real expulsion, with reasonable safety bounds on pathological states. A proposed 'gas-reducing food' may reduce **future gas formation** but may not subtract existing stored gas without an actual fart; this is now an explicit design constraint. State tests: no release over 10 game days, accumulation during cooldown, after digestion finishes, across reload, and at high pressure; **no gas loss** under any of those conditions.

## Distinct player versus animal intake models (2026-11-08)

**User distinction:** Vanilla Vintage Story players eat many times a day to replenish satiety, whereas penned animals can survive indefinitely **without being fed**; animal feeding commonly supports mating/offpsring rather than obligatory survival. Therefore do **not** force all eligible terrestrial animals through the player's repeatedly opened 30-second meal-collection timer or make animal farts depend solely on a rare observed feeding event.

**External verification:** [Vintage Story Animal husbandry wiki](https://wiki.vintagestory.at/Animal_Husbandry): vanilla animals do not require food for survival and cannot starve to death; trough/feed portions relate to reproduction. Compatible hunger mods such as [Feed or Fallow](https://mods.vintagestory.at/show/mod/65749) may alter that behavior, so our cosmetic simulation must not redefine hunger/starvation or interfere with reproduction/feeding mechanics. The game's own feeding AI may register animal consumption if appropriate food is available; do not assume every animal eats rarely when troughs are kept full.

**Architecture:** Share one deterministic per-food stomach→gut fermentation processor, gas reservoir, actual release and cooldown logic, but separate intake adapters and species profiles:
- **Players:** use preferred sliding 30-real-second inactivity **mixed-food batch** with deadline resetting (never additive) on each bite, finalizing/timestamping at inactivity closure. Independent mixed ingredients/quantity, frequent contributions.
- **Animals:** when a **real observed feeding event** is accessible (trough/hay/vegetables/prey/ground items as supported by species and actual API), create a per-event digestive contribution with the food/portion if known. No player-style 30-second collection window required initially. Verify which feeding hooks expose food identity; existing timestamps may reveal when something was eaten but not necessarily what. Never invent a cabbage meal from a generic 'recently fed' state.
- **Animal baseline:** a **low, species-weighted background intestinal gas contribution** independent of food identity, specifically so an unfed penned goat isn't permanently silent. This is an abstraction of unobserved biological processes, **not** an implied vanilla eating event, and not a new hunger/starvation system. On observed cabbage/other gas-prone foods, add delayed food-specific contribution on top of baseline. Keep baseline subtle enough that ~40 penned goats don't create continuous sound; actual fart requires stored gas and obeys pressure, movement/fear and cooldowns. Don't emit a backlog of effects after an unloaded entity returns; cap/aggregate reservoir safely.
- Distinguish broad species physiology/behavior via configurable profiles, without implementing heavy individual animal stomach queues when no food event is known. For player vs animal, use different **parameter sets**, not duplicate core engines. Model-dependent body size and sound profile could later affect sound category, release size and duration.
- **First release:** no burps; stomach remains a transit buffer only for actual food contributions. Baseline animal intestinal gas may bypass fictional stomach food records because it represents unobserved processes. Don't assume every land species has the same digestive tract physiology (e.g. ruminants vs carnivores).

**Design status:** clear user requirement to treat players and animals differently, numbers/rates and API handlers unapproved/unimplemented.

## Sliding 30-second inactivity meal batching — revised user preference (2026-11-08)

**Countdown clarification (2026-11-08):** The 30-second ingestion timer is a **resettable inactivity countdown, not an additive extension**. Each successful bite while a session is open sets `deadline = currentRealTime + 30 seconds` (equivalently, `remaining = 30s`), NOT `deadline += 30 seconds`. Thus 12 carrots cannot create a 6-minute *remaining* timer; the maximum remaining countdown at any instant is 30s. Continuous eating can still keep a session active for many minutes. When 30s of silence elapse, close and timestamp the entire meal at that closure. Keep per-food identities and quantities. This is a user-explicit correction; avoid conflating long total session duration with additive timer behavior.


**Important revision to the earlier fixed-window proposal:** User now **prefers exploring a sliding 30-real-second inactivity timer** for an eating **session**. The first successfully eaten food opens one pending meal. Every subsequent successful consumption, while pending, adds its exact food identity and quantity (including alternating carrot/peanut) **and refreshes the 30-second deadline**. Once the player goes 30 seconds without eating, finalize *one* mixed-food batch and **timestamp the stomach-queue entry at the moment the window closes**, as explicitly suggested by the user. The earlier assistant proposal of a fixed deadline and separate per-bite physiological start times is **not the current preferred model**. No code implemented; duration is tentative.

**Design consequence:** A persistent snacker could keep the same meal open for minutes or longer, delaying the earliest food's apparent stomach entry and intestinal fermentation. User recognizes this tradeoff and sees the value in limiting batch count. Possible **optional** safeguard: a maximum meal/session duration (e.g. several real minutes) in addition to the resettable inactivity timer, which would close one batch and begin a new one if still eating. **This cap is not user-approved; avoid implementing it as though settled.** A different compromise is keep oldest bite time as debug data but use closure time for digestion; that still deliberately delays processing. At vanilla default calendar speed (48 real min/24 game hours) the 30-real-second delay equates to 15 game minutes, typically modest.

**Pending-batch persistence:** store the in-progress food composition and time metadata so quitting/saving before timeout never loses consumed portions. Choose a clear game pause/sleep/server behavior for a *real-time* inactivity timer. Once finalized, store food sub-contributions in one composite stomach entry: different per-food gas potential, perhaps different transit and fermentation duration, no burp functionality. The queue entry can calculate delayed gas release for each ingredient and remove itself once all contributions finish; its produced gas remains in the separate shared reservoir. Subsequent sessions never reset earlier ones.

**Status:** design discussion; user has not explicitly settled hard cap, exact timing or batch-internal transit policy beyond the expressed close timestamp.

## Fixed 30-second food intake windows — design proposal (2026-11-08)

**User's new proposal:** Rather than recording each bite as a separate top-level meal, start a **fixed 30-real-second ingestion window with the first actually consumed food**; collect all subsequent successfully consumed foods in that window, then finalize the batch into the ongoing digestion queue. Food after the window closes starts the next fixed-length window. Do **not** extend/reset the deadline for every bite. An example deliberately alternates carrot, peanut, carrot, peanut; a batch must retain each food's distinct identity, portion count, gas potential and timing. Eating 16 carrots could span 2+ windows; each remains independent but enters the same overall digestion system.

**Proposed implementation refinement (not yet explicitly agreed):** Capture each bite at the exact moment it is successfully consumed with `Calendar.TotalHours`, amount and profile; group by 30 seconds of **server/active real elapsed time** for compact bookkeeping, **without shifting physiological start time to the end of the window**. A finalized batch has a collection of food-type sub-contributions (possibly grouped per food with sufficient timing information to preserve time-dependent gas potential) rather than a single average generic 'meal'. Food type order should not accidentally change total gas; preserve ingredient-specific stomach and fermentation curves. Batch progress is calculated from the contained bite timestamps even while the collection window is open. End-of-window is a bookkeeping event, **not a digestive gate**, and no gas is made in the stomach.

**Safety/persistence edge cases:** Preserve pending collection and individual bite times on save/reload, or safely finalize it on unload without changing digestion timing. If the user exits the world before the 30 seconds elapse, no eaten food may disappear. Respect changed calendar speeds, slow servers, world pause and time skips; record separate wall/active-session collection timing vs game-hour digestion timing. 30 seconds is a **tentative** grouping duration, not a settled physiological parameter. Food eaten when satiety is already at cap still counts if the game actually consumed it. Long snacking sessions become many bounded batches, not one ever-growing timer. Mixed foods and successive identical foods must test correctly.

## First-install unknown food, timestamped portion batches, and gas-production windows (2026-11-08)

User clarified the mental model as a rolling **stomach food queue/conveyor belt**: on first mod install, pre-existing satiety represents untracked food of unknown type/time; afterward the player may consume many pieces of one food (even 16 carrots to fill satiety) or a mixture of carrots, rice, cabbage, meat, peanuts. Each real consumption should have its **own time** and create an independent contribution; as contents transit the stomach they enter gut processing, produce food-specific intestinal gas gradually, then **stop contributing when the corresponding fermentation window ends**. Subsequent food cannot restart earlier food timers. These are current model-design discussions; exact durations and gas weights remain unapproved.

**Proposed first-attach policy:** Don't infer ingredient identity or time from vanilla satiety alone. When the mod is first attached to an existing player, initialize with **no tracked historical food**, leaving vanilla hunger unchanged; optionally allow tiny background spontaneous gas. This is a recommendation for user consideration, not a confirmed final decision. Subsequent loads must restore actual persistent per-entity stomach/gut contributions and reservoir, NEVER reset on login.

**Data model proposal:** Each successful eaten *portion* gets a `FoodContribution` with item/profile ID (and ingredient breakdown where possible), portion amount, consumed-at `Calendar.TotalHours`, stomach-transfer profile/duration, intestinal fermentation onset/duration and total available gas potential. Food can leave the stomach **gradually**; fermentation can be driven by how much material has reached its fermenting stage. Record exact consumption regardless of whether vanilla **satiety increase is capped at maximum**; conversely, do not count food never actually consumed. A short series of identical bites may be coalesced into a batch (e.g., 16 carrots eaten in minutes) **only if total amount and time-dependent future contribution are preserved**. Do not merge distant meals indiscriminately.

**Crucial distinction:** A food contribution has a **finite gas-production window** and eventually expires *after its entire potential has been accounted for*. That is **not a fart cooldown**. Gas already transferred to the separate **intestinal reservoir persists** even after the source food record expires; expulsion then depends on pressure, movement/crouch, chance, and distinct release cooldowns. Newly progressing foods can add to the same reservoir simultaneously. No burps/upper-gas mechanic for first release.

**Illustration only, not medically calibrated:** A morning carrot batch, a few cabbages, salted meat and peanuts each enter at their actual time. Their fermentation windows overlap several game-hours later; each generates its own curve, stops at its own expiry, and old gas remains in reservoir. Time speed changes and sleep/unload are handled via calendar hours + cumulative integrals, no retroactive sounds.

Design tests to include first ever install at partial satiety, 16 rapid carrots, near-full satiety food, 2+ mixed meals at different times, last meal not resetting old source, ending one fermentation while another continues, reservoir persisting after sources expire, and save/reload while one meal is partway digested.

## Digestion calendar and stomach-as-buffer model (2026-11-08)

**Explicit user requirement:** No **burping functionality** in the first development scope. Stomach is a **time/transit buffer** and produces no gas events or sounds. Future burping is a possible extension, but don't instantiate an unnecessary upper-gas reservoir in v1. This supersedes the historical statement near the top of the file about possible early upper gas; do not interpret that old line as current v1 scope. Keep a clean input→stomach→gut pipeline for future extension without coding burps now.

**Calendar verification (public Vintage Story API):** [`IGameCalendar.TotalHours`](https://apidocs.vintagestory.at/api/Vintagestory.API.Common.IGameCalendar.html) is absolute in-world hours; `HoursPerDay`, `TotalDays`, `SpeedOfTime` etc. expose settings. By default 24 game-hours/day take **48 real minutes**, so 1 game hour takes 2 real minutes. Altering calendar speed should **not require explicit conversion**: compare stamps and calculate `elapsedGameHours = max(0, nowTotalHours - priorTotalHours)`. Don't use `HourOfDay` modulo 24 to calculate duration. Respect game pause/sleep, worldtime speed and time skips. Distinguish date/time settings from satiety/hunger configuration; Vintage Story hunger depends on actions, equipment, environment, settings and may not scale identically with calendar speed.

**Real digestion research:** [Cleveland Clinic on digestive time](https://health.clevelandclinic.org/how-long-does-it-take-to-digest-food) explains stomach emptying is **gradual**, faster for simple carb/liquid and slower for mixed fatty/protein meals, often taking hours. [Mayo Clinic](https://www.mayoclinic.org/diseases-conditions/indigestion/expert-answers/digestive-system/faq-20058340) estimates combined transit stomach+small intestine ~6h average, with substantial variability. [NIDDK on intestinal gas](https://www.niddk.nih.gov/health-information/digestive-diseases/gas-digestive-tract/) explains large-intestine bacterial fermentation of remaining carbohydrates is an important source of flatus; stomach arrival by itself must not immediately produce release gas.

**Proposed (NOT approved numeric settings):**
- On successful food consumption create a **portion-aware independent meal contribution** with `consumedAtTotalHours`, weight/serving, per-ingredient gas potential and gastric transit profile; mix ingredient profile for bowls/cooked dishes if resolvable through API. Several meals may overlap in stomach and gut; no 'last meal reset'. Low-gas food occupies transit but adds little gas.
- Use continuous transfer (cumulative fraction/progress per meal) over an approximate **2–4 in-game-hour typical stomach window**, with adjustments for meal type and amount; no cliff at a single `readyAt`.
- Gut phase adds an **additional lag and gradual fermentation curve** after material leaves stomach; early proposed overall onset after eating **roughly 5–8+ game-hours** for average gas-producing mixed meal (for gameplay tuning, not a clinical threshold); some food earlier/later; gas rises as contributions overlap and reservoirs store until expelled.
- Keep game hunger/satiety **unmodified**, and do not use satiety drain rate as our digestion clock. Eating multiple times is simply multiple independent additive source events, not multiple resets. For 40 penned goats, bound active contributions and merge completed/near-identical ones **without losing remaining potential**.
- Per update advance `TotalHours` using deterministic cumulative curves; account correctly for jumps while entity is unloaded or asleep. Don't replay missed audio on catch-up, don't simulate every hour in a massive loop; use integrated deltas. Avoid time-negative progress on calendar corrections.
- Illustrative 24h day: cabbage consumed 08:00, begins leaving stomach progressively during ensuing hours, starts gas production some hours later; other meals at 11:00 and 15:00 each run on their own clocks while earlier gas persists. In default time, 3 game hours = 6 real minutes. If user chooses 96-min/day, 3 game hours = 12 real minutes automatically.

**State:** architecture discussion only; no code, no user approval for specific durations/curves. Before implementing we should establish gameplay feel and whether onset should be closer to realistic physiology or faster for comedic pacing. The key principles (no v1 burps, independent meals, game clock) are firm/planned as above.

## Emergent reactions to audible releases (user clarification, 2026-11-08)

**Confirmed design principle:** Any temporary herd commotion must arise **organically from existing individual creature mechanics**. At the level of a *single* animal:
- Normal digestion and food history build gas in upper/lower reservoirs according to game time. An animal with no stored gas cannot release it merely because it is startled.
- Any sound that the animal is actually configured to notice may cause an ordinary startled response, according to **its own** hearing radius, temperament, current fear/agitation, chance and ordinary AI state. A tiny/quiet fart should often attract no attention.
- Fear/startle/movement may increase that individual's chance of releasing **already stored** gas, using the same regular gas-release mechanics used everywhere; a release consumes its own reservoir and respects ordinary per-animal cooldowns.
- If that release is audible, nearby animals may each evaluate it independently under the **same** generic rules. If none responds, the chain ends; if others respond, further sounds are just ordinary sounds, not 'next stages' of a planned cascade.
- As each individual's gas depletes and normal fear dissipates, the herd naturally calms. All outcomes are contingent on current state, proximity, temperament and chance; there is no target count or desired crescendo.

**Technical constraint:** Vintage Story positional audio playback may not itself be sensed by animal AI. If needed, we can expose an ordinary local sound/stimulus notification from a gas release, handled by the same animal perception logic as any other relevant stimulus. This is an implementation signal, **not** a scheduled 'mayhem' gameplay event. Do not build a separate cascade manager, propagation-depth cap, global herd-frenzy meter, cascade budget or special `enableStartleCascade` mode. Rely on general per-entity reaction thresholds/cooldowns and bounded spatial/perception work for performance. Keep the distinction between sound being muted for client audio budget and an actual physical event available for server-side sensing.

This possibility should be tested *after* ordinary gas/AI behavior works, in a controlled survival pen containing 1, 5, then ~40 goats. Test for believable rare responses and performance, without tuning to guarantee any particular comedic outcome. No special mechanic is committed to first release.

The visible Physical group includes satiety, health, temperature, etc. The user prefers exploring a low-intrusion indicator there over an always-visible gas bar near the hunger HUD.

Present approximate, player-friendly **qualitative pressure levels** rather than precise percentages: e.g. `Comfortable`, `Building`, `Pressurized`, `Loaded`. Precise labels/thresholds still need balancing. The current upper and lower reservoirs are conceptually distinct; do not present inaccurate state when mixing them. Only reveal the player's own digestive status in multiplayer.

## Player crouch as natural pressure relief (revised proposal, 2026-11-08)

**Latest user request (supersedes the previous one-second-only crouch idea):** The player can deliberately relieve intestinal gas by crouching, with the outcome driven by **current lower-reservoir pressure** rather than a scripted two-part sequence. No need to have farted previously to use the quiet-relief path. User's 75% / 25% figures refer to **amount of gas in the reservoir**, not a 75% release probability.

- **Heavily loaded:** Holding crouch for **more than about 1 real-time second** creates a **high but non-guaranteed** chance of a normal fart. If it succeeds, release roughly **75% of the available lower-reservoir gas** at that time, leaving roughly 25% remaining; update the authoritative gas state. What constitutes heavily loaded and the precise probability remain to be tuned.
- **Lightly loaded (around 25% of capacity):** Crouching for **at least about 2 real-time seconds** lets the player **deliberately squeeze out the currently stored low amount** with a small randomly selected **squeaker** sound, without requiring an earlier full-pressure fart. If someone previously released 75% and has around 25% left, they may stand, crouch again for 2 seconds and clear it in exactly the same way.
- **No available gas:** No emission or fake sound at any crouch duration. Even after emptying the reservoir, digestion may later generate new gas normally.
- **One physical release per continuous crouch** is the initial proposed rule; no roll each frame and no immediate second squeaker on the same sustained crouch following the initial large release. If the heavy-pressure chance fails, behavior on extended crouching is to be balanced rather than silently auto-triggering a second event.
- **Cooldown / abuse:** Sensible regular cooldowns and minimum gas threshold; a deliberately held second crouch used to clear residual gas should be feasible without forcing players to wait an excessively long time. Do not let rapid repeated crouch tapping generate gas or spam sounds.
- **Server state:** Verify Vintage Story 1.22 supports authoritative detection of player crouch start, continuous duration, stand/cancel and multiplayer replication. Preserve the ordinary crouch/sneak function and avoid stealth debuffs. Any nearby-animal reaction follows the same *general audible-event perception* as all fart sounds; never script herd mayhem.
- **Player awareness:** Provide an unobtrusive way to judge whether the player is loaded enough to seek privacy. Start with a qualitative pressure status / diagnostic command, and consider optional lightweight UI or in-game cues later. No mandatory permanent meter or final pressure thresholds decided.

**Naming:** The technical ID `lingamsdigestivesim` is approved; the public display title **remains a variable/placeholder** until chosen.

**Status:** Design clarification only. None of these mechanics is yet implemented, and the game input/state APIs still require verification.

## Bear upright idle posture and gas-release opportunity (idea, 2026-11-08)

**User observation:** Vintage Story bears sometimes rise onto hind legs and look around. If the pose or associated AI task can be observed, its ordinary postural transition could momentarily make the bear somewhat more likely to release **existing** gas, as an incidental release during a stretch; do not generate gas or demand a sound. The underlying appearance may be an alert lookout pose rather than a true stretch. Avoid forcing a fart every time the bear stands up or creating any new bear animation.

**API research:** The [game bear wiki](https://wiki.vintagestory.at/Bear) confirms occasional hind-leg standing; [IAnimationManager](https://apidocs.vintagestory.at/api/Vintagestory.API.Common.IAnimationManager.html) has `IsAnimationActive(params string[] anims)`; [entity AI debug documentation](https://wiki.vintagestory.at/Modding:Entity_Behavior_taskai) identifies `/entity debug 1` on server plus `.clientconfig showentitydebuginfo 1` on client to see active tasks and animations. The existing [Noisy Bears](https://mods.vintagestory.at/noisybears) mod uses JSON AI task sound hooks to produce a growl on hind-leg standing (historical versions, not tested for 1.22). **Exact bear animation/task code and server visibility have not been inspected in an installed 1.22 build.**

**Potential implementation:** Discover the actual posture task/animation first. Upon transition to standing upright, **wait approximately one real-time second** before evaluating a one-time, small release-probability opportunity; do not emit gas at the instant the bear rises. At the time of evaluation verify the bear remains upright, is alive, has sufficient stored gas and is not on release cooldown. An unsuccessful roll is normal: standing never guarantees a fart, and nothing should be forced on the animation. If the bear lowers itself before the delay ends, cancel the pending opportunity. Avoid rolling every tick while upright. Use the same per-entity gas reservoir and ordinary release logic as other movement/posture influences. The one-second value is an initial user-suggested tuning point, subject to in-game testing. If animations are client-only, prefer a validated server AI-task state or equivalent rather than a client-authored release.

**Test:** Observe a wild bear in an isolated throwaway survival test world with entity debugging active. Confirm precise animation/task codes while upright; verify that no special release occurs if reservoir is empty, that the bear can stand normally without farting, and that movement/AI is unchanged. Do not disturb the user's established world merely to test this.
